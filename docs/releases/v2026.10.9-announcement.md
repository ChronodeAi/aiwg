# AIWG 2026.10.9 - Consistent sensitive-value handling

AIWG 2026.10.9 completes #3079: one consistent way to supply sensitive values.
The final slices let resource commands, daemon and messaging configuration,
and storage backends use shared credential sources. They also keep credentials
out of unrelated children and reflected errors, tighten UHP profile validation,
and make intentional secret disclosure in diagnostics explicit.

This release covers the five merged PRs since 2026.10.8. The completion applies
to the documented public input inventory; provider-owned authentication and
recipient exceptions retain their existing contracts. The
[sensitive-value guide and inventory](https://github.com/jmagly/aiwg/blob/v2026.10.9/docs/cli/sensitive-values.md)
records those boundaries and developer-only live tooling follow-ups.

## Daemon and messaging

Daemon configuration can keep references instead of secret bytes. The existing
loader resolves each active recipient's credentials at startup and reload,
without prompting or replacing references in saved JSON/YAML (#3079, #3623).

| Recipient | Configuration field |
| --- | --- |
| Web UI | `interface.web.token_ref` |
| Webhook configuration | Existing `webhook.secret_env` |
| Telegram and Discord | `messaging.<adapter>.botToken_ref`, with `token_ref` as an alias |
| Slack bot | `messaging.slack.botToken_ref` |
| Slack webhook | `messaging.slack.webhookUrl_ref` |

Each field accepts `ENV_NAME`, `file:ABSOLUTE_PATH` or `store:NAME`. Existing
`${ENV_NAME}` templates still resolve. Explicit references take precedence over
literal values and legacy environment variables. Missing or invalid selected
`*_ref`, file or store input fails startup without fallback. The webhook's
legacy environment-name lookup stays optional when unset.

**Upgrade advice:** literal config secrets still work but warn once per config
instance, without printing values. They remain on disk and are not migrated.
Move them to the recipient's reference field. `daemon-init` copies references
only. Web authentication remains disabled when no token is configured; set a
token deliberately if authentication is required. See the
[daemon guide](https://github.com/jmagly/aiwg/blob/v2026.10.9/docs/daemon-guide.md).

Each web or messaging consumer receives its own resolved config. Agent, chat,
maintenance and npm-watcher children no longer inherit daemon secret names or
resolved values, while keeping provider and npm configuration. Adapter errors
and config parse failures avoid echoing credentials. Configured messaging
credentials can enable their adapter; standalone adapter constructors keep
their existing literal/environment contract.

**Webhook limitation:** the secret resolves into recipient-local configuration,
but the daemon has no inbound webhook listener yet. This release adds no HTTP
receiver and does not change inbound webhook delivery behavior (#3623).

## Storage backends

Storage credentials resolve at the backend boundary, so the same references
work for testing, migration, corpus import and other operations using that
backend. No backend prompts or reads stdin (#3079, #3625, #3627; closes #3620).

| Backend | Selector and behavior |
| --- | --- |
| Logseq | `apiTokenEnv` accepts `ENV_NAME`, `file:ABSOLUTE_PATH` or `store:NAME`. Omitted selection retains `LOGSEQ_API_TOKEN`. |
| PostgreSQL | `connectionStringEnv` gains `file:` and `store:` alongside environment names; its default remains `AIWG_POSTGRES_URL`. |
| PostgREST | `authorizationEnv` gains `file:` and `store:` alongside environment names. Its value is the complete Authorization header, including any `Bearer ` prefix. Omitted selection stays unauthenticated. |
| Fortemi | Existing MCP registry `headerEnv` / `envFrom` references continue to resolve at connection time. Redaction now also covers legacy literal headers and environment credentials. |

Missing selected sources fail without falling back. Logseq keeps its optional
default behavior: a missing default token warns and filesystem writes continue;
an explicit missing reference fails when API use is enabled. With
`useApi: false`, no credential is read. See the
[Logseq guide](https://github.com/jmagly/aiwg/blob/v2026.10.9/docs/storage/backends/logseq.md).

PostgreSQL driver failures and decoded PostgREST HTTP errors and logs no longer
expose connection strings, passwords or authorization values. Fortemi transport
errors, logs and results redact registry credentials; credential-bearing stdio
connections drain recipient stderr privately and refuse Node child-process
debug logging before spawn (#3625, #3627). The
[PostgreSQL](https://github.com/jmagly/aiwg/blob/v2026.10.9/docs/storage/backends/postgres.md),
[PostgREST](https://github.com/jmagly/aiwg/blob/v2026.10.9/docs/storage/backends/postgrest.md)
and
[Fortemi](https://github.com/jmagly/aiwg/blob/v2026.10.9/docs/storage/backends/fortemi.md)
guides describe the configuration contracts; TLS policy and routing stay the same.

The storage claims gate can now accept a documented detached reference run
when it records branch `HEAD`, its public base commit and the exact modified
sources inside the claim scope, all bound by the source digest. Main evidence
still comes from main. The existing tool gains
`node tools/benchmarks/verify-storage-claims.mjs --import-server-run <run-metadata.json>`
to import emitted reports and Vitest results into the evidence format (#3627).
The [qualification guide](https://github.com/jmagly/aiwg/blob/v2026.10.9/docs/storage/qualification.md)
documents the procedure. Changed registered source bytes require requalification.

## CLI resource access

`aiwg discover`, `show`, `resource-versions` and `use` can obtain the protected
release bearer without putting its value on the command line (#3079, #3622):

- `--resource-token-interactive` requests hidden terminal entry.
- `--resource-token-stdin` explicitly reads piped input.
- `--resource-token-file <path>` selects a private file.
- `--resource-token-store <name>` selects a named OS-store entry.
- `--resource-token-env <NAME>` selects an environment variable by name.

When several sources are supplied, the order above applies. Explicit sources
precede the existing `AIWG_RESOURCE_TOKEN_FILE`, then
`AIWG_RESOURCE_TOKEN`, then auth-store access-token lookup. Selected empty or
inaccessible input fails without fallback. No prompt appears unless the
interactive flag is selected. Without an explicit source, public/offline
resolution stays unchanged; offline cache reads do not look up implicit
credentials.

`aiwg use` applies this bearer to its existing signed release receipt lookup;
the flags do not add web deployment support. It withholds the resource bearer
variables from deploy scripts.
Resource requests and stream errors redact reflected bearer values.
`AIWG_RESOURCE_TOKEN_FILE` now uses shared private-file validation. Files must
be private, user-owned, regular, non-symlink and single-link. Replace linked or
exposed files before upgrading. Windows file input refuses until native ACL
validation is available; stdin and store input remain alternatives where
supported. See
[web-backed resources](https://github.com/jmagly/aiwg/blob/v2026.10.9/docs/cli/web-backed-resources.md).

**UHP upgrade advice:** profiles reject extra inline credential locator fields.
Keep only `credential.source: env` and `credential.name`; UHP remains
environment-reference-only. The existing provider-recipient environment
exceptions are documented in the sensitive-value guide, including the narrower
qualified worker lists (#3079, #3625). See the
[UHP client guide](https://github.com/jmagly/aiwg/blob/v2026.10.9/docs/uhp-client.md).

## Hooks and reliability

The SessionStart hook now waits up to 5 seconds for late nonblocking stdin.
Previously, `EAGAIN` could be treated as missing input under load, silently
losing the decision-offload compact anchor. The source and bundled plugin hook
both include the fix; EOF, size limits and invalid JSON behavior stay the same
(#3621).

`aiwg diagnose --include-secrets` now warns on stderr that its output contains
secrets and must be reviewed before sharing, including when `--stdout` is
selected. Help states the same disclosure behavior. Default sanitization is
unchanged; the flag still deliberately disables it (#3079, #3625). See the
[CLI reference](https://github.com/jmagly/aiwg/blob/v2026.10.9/docs/cli/reference.md).

## Evidence

No live provider comparison ran for this release. Before merging, each slice
went through a full local CI-equivalent run of every CI lane, with about 27,000
default-lane tests:

- The 4a run surfaced a load-dependent SessionStart hook bug. It was fixed first, in #3621.
- The 4b run caught a regression in the npm provider watcher, which was fixed before merge.
- The remaining failures were timeouts under host load in tests the slices did not
  touch. They passed when rerun on their own, and one is tracked in #3626.

Main CI passed after every merge.

The PostgreSQL/PostgREST reference benchmarks were requalified locally on
disposable loopback containers with pinned image digests and Node 24.22.1
(#3627). Direct PostgreSQL passed 6 live tests with no skips; PostgREST passed 4,
with 1 authenticated-RLS test skipped because the run had no JWT authority.
These reference-host results do not establish production or remote-service
certification. See
[storage qualification](https://github.com/jmagly/aiwg/blob/v2026.10.9/docs/storage/qualification.md).

## Upgrade

Update using your existing installation method, then refresh deployed frameworks
and addons. Move daemon literals to references; choose explicit resource bearer
sources when needed; and use backend selectors for file/store credentials.
Keep the whole Authorization value in a PostgREST source. Check private-file
permissions and replace linked files, remove extra UHP credential fields, and
review any diagnostic bundle that intentionally includes secrets before sharing.

[changelog](https://github.com/jmagly/aiwg/blob/v2026.10.9/CHANGELOG.md#2026109---2026-10-26)
